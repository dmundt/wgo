# Contributing to wgo

Thanks for contributing. wgo is a direct, byte-for-byte port of
[WireViz](https://github.com/wireviz/WireViz) v0.4.1 — keep it that way.

## The parity rule

Output files (`.gv`, `.svg`, `.png`, `.html`, `.bom.tsv`) must stay
**byte-identical** to the reference WireViz 0.4.1 implementation. The golden
tests and the `parity` CI job enforce this. Before opening a PR, make sure:

- `go test ./...` passes, including the golden tests.
- If you changed output logic, run the parity check (`make parity`) or at least
  regenerate goldens (`make golden`) and confirm the diff is expected.

Console messages and exit codes follow WireViz too. If you must change them,
call it out in the PR description.

## Development

Prerequisites: Go 1.25+, Graphviz `dot` on `PATH` (for svg/png/html tests).

```
make fmt       # gofmt check
make vet       # go vet
make test      # full test suite incl. golden outputs
make lint      # golangci-lint (v2)
make bench     # benchmarks
make fuzz      # run parser fuzzers for 15s each
```

## Golden outputs

Goldens in `testdata/golden` were generated by WireViz 0.4.1 on Windows with
Graphviz 15.1.0. They are environment-bound: svg/png/html goldens only run
when `dot` is on `PATH`. To regenerate:

```
python -m venv .venv
.venv/Scripts/pip install wireviz==0.4.1
.venv/Scripts/wireviz -f ghtsp -O <name> testdata/<name>.yml
# copy outputs into testdata/golden/
```

## Branching and PRs

- `main` is protected by a ruleset: PRs require 1 approval and all CI checks.
- Make one logical change per PR. Small PRs merge fast.
- If a change spans the panic/error handling or package layout, expect a review
  focused on the parity rule above.

## Commit messages

Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`, ...),
imperative mood, subject under 50 chars. A body only when the *why* is not
obvious.

## Issues

Include: wgo version (`wgo -V`), input YAML (or a minimal reproducer), the
expected output vs. what you got, and whether the reference WireViz agrees.
